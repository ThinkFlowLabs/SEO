Indexing & crawl control
A1Self-canonical every blog post & chef profile

Every page should declare itself as its own canonical. Today they all point elsewhere, so 16 months of equity lands on the wrong URL.

P0eta1 dev day
▶ Audit reference & how to fix
Where it is in the audit Section 02 "What's actually holding the site back," Finding 1 ("The blog's canonical tag is sending equity to the wrong page"). Also Section 03 "Quick Wins," row 1. Impact quoted: 44,845 impressions on one post produced 39 clicks (0.09% CTR).

Audit's fix (verbatim): Set <link rel="canonical" href="{currentURL}"> per post (self-canonical). Same fix on /become-a-personal-chef (currently canonicals to /career/) and on every /chef/* profile (currently no canonical).

Concretely: one template change so each URL emits its own canonical. Expected lift: 10 to 30x CTR on the affected URLs with no ranking change required.

A2Consolidate the duplicate hosts (301s)

The same content is indexed across five hostnames. Point them all at the canonical host and move the Substack blog in-house.

P0eta~2 dev days
▶ Audit reference & how to fix
Where it is in the audit Section 02, Finding 2 ("Five subdomains are indexing the same content as four different sites"). Also Section 03 "Quick Wins," rows 2 and 9. Hosts listed: https://chefpost.com (canonical), http://chefpost.com (still indexed, 27,216 imp / 424 clicks), www., booking.chefpost.com, blog.chefpost.com (Substack).

Audit's fix (verbatim): Force 301 redirects to the canonical https://chefpost.com/{path} at the edge for every non-canonical host. Migrate the Substack blog into /blog/ with 301s.

Concretely: edge rules on Vercel/Cloudflare for the redirects; then 301 every old Substack URL to its new /blog/ path. Reclaims the 424 monthly clicks bleeding to http:// and consolidates link equity.

A3Get dev & back-end out of Google

The development server is sitting in Google's index. Lock it out, and deindex the back-end and booking records.

P0eta~1 hr to 1 day
▶ Audit reference & how to fix
Where it is in the audit Section 02, Finding 2 (the dev.chefpost.com line: "your development server is in Google's index. This is a security and SEO problem"). Also Section 03 "Quick Wins," row 3.

Audit's fix (verbatim): Immediately add HTTP basic auth to dev.chefpost.com + robots.txt: Disallow: / + X-Robots-Tag: noindex.

Concretely: plus the two records you agreed to delete on the call, the backend and booking subdomains. Security win and crawl-budget recovery.

Templates: schema & headings
A5Ship the schema layer in the template core

There is zero schema on the whole site today. Bake JSON-LD into the templates in phases so every page inherits it, old and new.

P0eta2 + 3 + 5 days (phased)
▶ Audit reference & how to fix
Where it is in the audit Section 02, Finding 3 ("There is zero schema.org markup anywhere on the site"). Full rollout in Section 06 "Schema Markup Plan," which also gives copy-paste reference JSON-LD (FAQPage on /faq, and Service + LocalBusiness on a city page).

Phase 1 (2 dev days): Organization (sitewide), WebSite + SearchAction (homepage), FAQPage (/faq + every blog post), BlogPosting (every blog post), BreadcrumbList (every template).

Phase 2 (3 dev days): Person + LocalBusiness on every /chef/*, Service on /meal-prep, /events and every city page, AggregateRating on chef profiles with reviews, MenuItem on every Event. Add the price-range Offers Jimmy supplies in B3 (hidden from visitors, read by Google and AI).

Phase 3 to 4 (5 dev days): Recipe on blog posts with a menu, HowTo on guides, Event on yacht and holiday experiences, VideoObject for chef intro videos, ItemList on /filter.

Performance & automation
A9Fix Core Web Vitals (mobile LCP 6.1s)

Mobile Performance is 0.65 and LCP is 6.1s. The site cannot rank competitively until this is under 2.5s.

P1eta3 to 5 dev days
▶ Audit reference & how to fix
Where it is in the audit Section 02, Finding 5 ("Mobile LCP is 6.1 seconds"). Also Section 03 "Quick Wins," rows 7 and 10. Numbers: Lighthouse mobile Perf 0.65, LCP 6.1s (good is under 2.5s), 4 render-blocking JS + 3 render-blocking stylesheets, /meal-prep LCP 4.5s. A placeholder GA4 ID G-12345HHDSD is firing next to the real G-41JH1G30DC.

Audit's fix (verbatim): Defer + async the 4 blocking scripts; inline critical CSS for the hero; serve a real LCP image (hero photo) with fetchpriority="high" and width/height attributes; preconnect the analytics domains; drop the accessibility-overlay widget (adds 200kb of JS). Remove the placeholder GA4 ID.

Target: LCP under 2.5s, Performance over 0.85.

A10Cron: auto-rebuild sitemap + robots weekly

A scheduled job that regenerates the sitemap and robots files and drops disabled chef/product URLs automatically.

P1eta0.5 day
▶ Audit reference & how to fix
Where it is in the audit Not a numbered finding, this one came from the call. It supports the indexing hygiene in Section 02 (Findings 1 to 3): the sitemap must always reflect live, canonical URLs only.

What to do: a cron job that rebuilds sitemap.xml and robots.txt, removing any chef or product that has been disabled since the last run.

Cadence: weekly was agreed on the call (content ships about weekly, so daily would waste crawl budget). A timer at, say, Monday 00:00 is fine.
